# Подготовка среды и организация работы

## 1. Разобраться в структуре проекта

Перед запуском обучения найдите входные данные, код предобработки и место сохранения модели. Если изменить один из этих элементов без учета остальных, рабочая модель легко превращается в несовместимый набор файлов.

| Путь | Назначение |
| --- | --- |
| `src/data/`, `src/features/` | Загрузка, очистка, валидация и вычисление признаков |
| `src/neural/` | Исходная PyTorch NN, экспорт, quantization, benchmark |
| `src/api/`, `src/frontend/` | HTTP-контракт модели и пользовательская форма |
| `src/monitoring/`, `src/model_management/` | Drift и маршрутизация разных версий |
| `src/retraining/`, `airflow/dags/` | Переобучение и его оркестрация |
| `infrastructure/` | Terraform и Kubernetes |
| `monitoring/` | Prometheus/Grafana/Loki и инструкции |
| `.github/workflows/` | CI/CD |
| `tests/` | Автоматические проверки |
| `reports/` | Итоговые метрики и проверяемые результаты |
| `artifacts/` | Локальные промежуточные результаты экспериментов |

Пути задаются в [src/config.py](../src/config.py). Не подставляйте случайные файлы с похожими именами: scaler должен соответствовать модели, а порядок признаков — обучению.

## 2. Подготовить Python

Используйте Python 3.13 и зависимости, закрепленные в `uv.lock`:

```bash
uv sync --locked --group dev
source .venv/bin/activate
python --version
make help
```

Группа `dev` включает DVC, мониторинг и инструменты проверки. Для обычной работы можно использовать `uv run`, который выбирает окружение проекта. При ручном вызове `python` сначала активируйте `.venv`.

Если `uv sync` не проходит, сначала прочитайте сообщение: несовместимая версия Python, отсутствие сети и ошибка сборки пакета имеют разные решения. Не начинайте с удаления lock-файла: он нужен для воспроизводимости среды.

Для контейнерных этапов дополнительно нужны работающие Docker/Compose. Для kind-сценариев — kind, kubectl и доступ Docker к скачиванию образов. Для этапа 2 — Terraform. Установщики локальных Kubernetes-инструментов описаны в [инструкции этапа 3](../infrastructure/kubernetes/README.txt).

## 3. Получить и проверить данные

```bash
make data
make prepare-data
uv run python -m pytest tests/test_data.py tests/test_validation.py -q
```

`make data` загружает исходный CSV и вызывает подготовку; `make prepare-data` позволяет отдельно повторить подготовку уже имеющихся данных. Исходный путь — `data/raw/UCI_Credit_Card.csv`, обработанный — `data/processed/UCI_Credit_Card.csv`.

Проследите последовательность: исходные колонки → правила валидации → очистка → дополнительные признаки. Проверка диапазонов позволяет остановить ошибку до обучения. Тест с аномальными данными должен успешно обнаружить нарушение: ожидаемое исключение внутри такого теста означает исправность защитного механизма.

Не используйте тестовую выборку для обучения scaler. Иначе статистика будущих объектов попадает в обучение и искажает оценку качества.

## 4. Понять различие Git и DVC

Git хранит код, конфигурации и компактные материалы для сдачи. DVC хранит ссылки и зависимости больших данных/моделей, а сами содержимые помещает в кеш и настроенный remote. `dvc.yaml` описывает команды и зависимости стадий, `dvc.lock` фиксирует хеши конкретных результатов.

```bash
uv run dvc status
uv run dvc repro
uv run dvc metrics show
```

`dvc repro` может запустить обучение классической модели и изменить локальные результаты. Для него нужны исходные данные и зависимости; если обучение использует tracking server, сначала запустите `make mlflow` в другом терминале согласно основному README. `dvc pull` возможен только с настроенным и заполненным remote; сам факт наличия `.dvc/config` не загружает отсутствующий датасет из интернета.

NN/ONNX не включены в текущую стадию `train` DVC. Воспроизводимая версия нейросети должна связывать веса, scaler, ONNX, порядок признаков, данные и commit кода. Хеш одного ONNX-файла не описывает предобработку.

## 5. Что исключается из Git

В `.gitignore` исключены локальные среды, кеши, секреты, runtime-артефакты, настройки ассистента/редактора, журналы CatBoost. Папка `docs/` не исключена и доступна для добавления в Git. Примеры `.env.example` и `.env.dvc.example` остаются доступными для добавления в Git: в них описываются имена параметров без настоящих ключей.

В отличие от временных логов, `reports/benchmark/`, `reports/quantization.json`, отчеты PSI и итоговый отчет непосредственно подтверждают учебную задачу. Их не следует скрывать целиком. `uv.lock`, Terraform lock-файлы, DVC metadata, тесты и workflows также являются частью воспроизводимой работы.

```bash
git status --short
git status --short -- docs/
git check-ignore -v notebooks/catboost_info/learn_error.tsv
git ls-files .agents notebooks/catboost_info
```

Последняя команда после исключения уже отслеживавшихся файлов не должна выводить их пути. `.gitignore` действует на неотслеживаемые файлы; для ранее добавленного файла требуется `git rm --cached`, который убирает запись из индекса, сохраняя содержимое на диске. Это изменение вступит в историю при следующем коммите.

Не применяйте `git rm -r --cached .` ради одного исключения: точечное изменение проще проверить. Для добавления гайда достаточно обычного `git add docs/`; принудительное добавление не требуется.

## 6. Базовая проверка перед этапами

```bash
uv run python -m pytest tests -q -ra
uv run black --check src tests scripts docker/backend-entrypoint.py
uv run flake8 --jobs 1 src tests scripts docker/backend-entrypoint.py
git diff --check
```

`passed` означает выполненные проверки, `skipped` — пропуски, причину которых нужно прочитать. Отсутствие Streamlit пропускает UI-тесты, отсутствие kubectl — проверки рендеринга. Это не подтверждение исправности пропущенной части.

В аудите от 26.11.2026 получено 73 passed и 7 skipped; Black потребовал форматирование `scripts/stage6_monitoring.py`. Здесь приводится результат аудита, а не обещание такого же результата после любых последующих изменений.
