# Этап 5 Метрики логи и реагирование на инциденты

## Цель этапа

Научиться отвечать на вопросы «работает ли сервис», «почему он замедлился» и «что делать при отказе». Наличие запущенной Grafana еще не означает наличие мониторинга: данные должны поступать, запросы панелей — возвращать нужные ряды, алерты — срабатывать и разрешаться после восстановления.

Основные материалы: [мониторинг](../monitoring/README.md), [правила Prometheus](../monitoring/prometheus/alerts.yml), [дашборды](../monitoring/grafana/dashboards), [runbook](../monitoring/RUNBOOK.md).

## Шаг 1 Разделить источники наблюдений

| Компонент | Что наблюдает |
| --- | --- |
| API `/metrics` | HTTP-запросы, прогнозы, ошибки и длительность inference |
| node exporter | CPU, память, диск хоста |
| cAdvisor | Потребление ресурсов контейнерами |
| Prometheus | Регулярно собирает и хранит численные временные ряды |
| Alloy и Loki | Собирают и хранят события журналов |
| Grafana | Строит панели и запросы к метрикам/логам |
| Alertmanager | Группирует и показывает/маршрутизирует алерты |

Метрики дают картину во времени, лог помогает понять конкретное событие. Версия модели задается `MODEL_VERSION`; без нее труднее отличить ухудшение новой модели от изменения трафика. Не помещайте request ID и признаки клиента в labels метрик: число уникальных рядов может стать огромным.

## Шаг 2 Запустить обычный локальный стенд

Подготовьте ONNX и scaler из этапа 1. Затем задайте локальный пароль Grafana в оболочке:

```bash
read -rsp 'Пароль Grafana: ' GRAFANA_ADMIN_PASSWORD
export GRAFANA_ADMIN_PASSWORD
make monitoring
```

Проверьте состояние контейнеров:

```bash
docker compose -f docker-compose.yml -f docker-compose.monitoring.yml ps
curl --fail http://127.0.0.1:8000/health
curl --fail http://127.0.0.1:8000/metrics
```

Адреса: Grafana `http://localhost:3000`, Prometheus `http://localhost:9090`, Alertmanager `http://localhost:9093`, readiness Loki `http://localhost:3100/ready`. Grafana использует логин `admin` и заданный пароль.

Сервисы мониторинга предназначены для локального доверенного Docker-хоста. Если Docker socket недоступен Alloy или cAdvisor не видит ресурсы контейнеров, сначала исследуйте mounts/права, а не меняйте Grafana-запросы.

## Шаг 3 Создать полезный трафик

В другом терминале выполните `make test-api`, затем откройте Prometheus Targets и дашборды Grafana. Убедитесь, что счетчик прогнозов растет и target API имеет состояние UP.

Пустой график может означать отсутствие запросов, неверный временной диапазон, неподходящий label или недоступный источник. Начинайте с простого ряда `up`, затем проверяйте конкретную метрику. Grafana не создает данные, которых нет в Prometheus.

Histogram хранит распределение по buckets. p95 вычисляется из скоростей прироста buckets за окно; это не среднее время и не максимальный запрос. При редком трафике значение хвостового квантиля интерпретируется осторожно.

## Шаг 4 Проверить правила до инцидента

```bash
uv run python -m pytest tests/test_observability.py tests/test_api_readiness.py -q

docker run --rm -v "$PWD/monitoring/prometheus:/etc/prometheus:ro" \
  --entrypoint promtool prom/prometheus:v3.2.1 \
  check config /etc/prometheus/prometheus.yml

docker run --rm -w /etc/prometheus \
  -v "$PWD/monitoring/prometheus:/etc/prometheus:ro" \
  --entrypoint promtool prom/prometheus:v3.2.1 test rules test-alerts.yml
```

Unit-тесты правил используют синтетические временные ряды и помогают проверить пороги без ожидания реального переполнения диска. Они дополняют интеграцию Alertmanager, но не подтверждают внешнюю доставку уведомления.

В проекте есть ScoringDown, ScoringErrors, ScoringLatency, HostMemoryHigh, HostDiskLow и MonitoringTargetDown. `for` означает требуемую длительность нарушения: между первым плохим измерением и firing проходит время. Краткая ошибка может исчезнуть, не дойдя до алерта.

## Шаг 5 Выполнить изолированный эксперимент

```bash
make monitoring-experiment
```

Команда собирает тестовый backend и запускает сценарий с сохранением стенда. Используются настоящие ONNX/scaler для успешных запросов и управляемая инъекция ошибок для проверки инцидентов. Эксперимент требует свободных стандартных портов: обычный стенд `make monitoring` не должен одновременно занимать те же порты.

Сценарий проверяет метрики приложения/хоста/контейнеров, Grafana, поступление логов, метрические и логовые алерты, недоступность API, восстановление и разрешение алертов. Такой эксперимент проверяет всю цепочку:

```text
ошибка → событие/метрика → правило → Alertmanager → восстановление → resolved
```

Если используется одноразовый вариант `uv run python -m scripts.test_observability_local`, предварительно соберите `docker build -t credit-backend:observability .`. Без `--keep` сценарий удаляет свой тестовый стенд после проверки.

## Шаг 6 Читать runbook как алгоритм

Для каждого алерта нужен порядок: подтвердить проблему, проверить источник, ограничить воздействие, восстановить сервис, проверить результат. Например, при ScoringDown сначала смотрят target и контейнер API, затем readiness и загрузку модели. Перезапуск всех контейнеров сразу может стереть диагностические признаки и создать новый простой.

Для ScoringErrors выясните, это 422 от неверного клиента или 5xx во время inference. В проекте 422 входит в HTTP-метрики, но не считается ошибкой вычисления модели. Для latency проверьте нагрузку, ресурсы и версию модели до изменения лимитов.

У Alertmanager настроен локальный receiver UI. Внешняя отправка в почту/мессенджер без отдельного receiver не происходит. Для учебного результата достаточно подтвержденной локальной доставки.

## Шаг 7 Остановить нужный стенд

```bash
make monitoring-down
```

Это остановка обычного monitoring. Если запускали изолированный эксперимент, используйте его собственную команду:

```bash
make monitoring-experiment-down
```

Volumes сохраняются. Не добавляйте `-v`, если хотите оставить историю. Каждый стенд имеет собственный Compose project: диагностируйте и останавливайте именно тот, который запускали.

## Результат и самопроверка

Сохраните конфигурации scrape, dashboards, правила и runbook, а в протоколе — события firing/resolved и ответы проверочных запросов. Объясните, чем target UP отличается от корректного качества прогнозов, почему отсутствие метрики не равно нулю и почему реакция на инцидент включает проверку восстановления.

Качество и дрифт рассматриваются на [этапе 6](06_drift_and_seldon.md).
