# Этап 2 Инфраструктура как код на Terraform

## Цель этапа

Описать инфраструктуру так, чтобы ее состав и параметры можно было проверить до создания ресурсов. В учебном объеме достаточно конфигураций, инструкций и локальных mock-тестов. Облачный аккаунт и платные ресурсы для этой главы не нужны.

Основной источник команд — [infrastructure/README.txt](../infrastructure/README.txt). Модули находятся в `infrastructure/modules/`, окружения — в `infrastructure/environments/`, отдельный bootstrap state — в `infrastructure/bootstrap/`.

## Шаг 1 Разобрать границы модулей

| Модуль | Ответственность | Зачем выделять отдельно |
| --- | --- | --- |
| `network` | VPC и подсети | Единая сетевая основа для компонентов |
| `kubernetes` | Managed Kubernetes, node groups, IAM и security groups | Изоляция конфигурации кластера |
| `storage` | Object Storage | Версионирование и ограничения доступа к артефактам |
| `monitoring` | Облачные ресурсы наблюдаемости | Платформенные логи и метрики |
| `compute` | Дополнительная VM | Отдельный вариант вычислительного узла |

Переменные — входной контракт модуля, outputs — результаты, которыми пользуется окружение. Изучая `main.tf`, проследите передачу network/subnet ID в Kubernetes. Это граф зависимостей, по которому Terraform определяет порядок действий.

Yandex Cloud выбран потому, что нужные сервисы описываются одним провайдером. Этот аргумент не равнозначен доказательству минимальной стоимости: тарифы и фактическая нагрузка здесь не сравниваются.

## Шаг 2 Разделить staging и production

Окружения используют общие модули, но получают собственные параметры и state. Изменение production не должно случайно затронуть staging или наоборот.

Изучите `variables.tf`, `terraform.tfvars.example`, `providers.tf` и `main.tf` обоих окружений. Файлы `.example` показывают обязательные параметры; настоящие `terraform.tfvars`, ключи и `backend.hcl` исключены из Git.

Для локальной проверки не заполняйте реальные ID. В mock-тестах используются тестовые значения, включая тестовую версию Kubernetes. Они не обещают доступность этой версии в облаке.

## Шаг 3 Понять state и bootstrap

State связывает ресурс в конфигурации с конкретным созданным объектом. Он не является исходным кодом и может содержать чувствительные сведения.

Backend S3 задает разные ключи:

```text
staging/terraform.tfstate
production/terraform.tfstate
```

Bootstrap отдельно описывает бакет для состояния. Он нужен потому, что backend не может сохранить state в еще не существующий бакет. Бакет state отличается от бакета модельных артефактов: у них разные назначения и доступы.

В текущей конфигурации S3 backend не предоставляет распределенную блокировку. Версионирование бакета дает историю, но не предотвращает параллельные записи. Для будущего реального запуска операции одного окружения должны выполняться последовательно.

В учебной проверке бакет не создается, credentials для backend не нужны. Ключевой параметр локальной инициализации — `-backend=false`.

## Шаг 4 Выполнить локальную проверку

```bash
bash infrastructure/scripts/check-local.sh
```

Скрипт делает `fmt -check`, локальную инициализацию с отключенным backend, `validate`, `terraform test`, статическую проверку NetworkPolicy и синтаксиса shell. Первый `init` может скачать провайдер; mock-тесты облачные ресурсы не создают.

Чтобы разобрать последовательность вручную:

```bash
terraform fmt -check -recursive infrastructure
terraform -chdir=infrastructure/environments/staging init -backend=false -input=false
terraform -chdir=infrastructure/environments/staging validate
terraform -chdir=infrastructure/environments/staging test
```

Повторите validate/test для production, bootstrap, modules/kubernetes и modules/storage. Скрипт автоматизирует эти повторы и останавливается при ошибке.

Ожидаются 14 успешных сценариев: staging 4, production 4, bootstrap 1, Kubernetes 3 и Storage 2. `terraform test` из корня проекта не заменяет запуск в этих каталогах.

## Шаг 5 Прочитать тесты как спецификацию

Откройте `tests/*.tftest.hcl` внутри соответствующих каталогов. `mock_provider` заменяет обращения к облачному API. Тест может проверить, что CPU-группа не имеет GPU, мастер описан в трех зонах, бакет закрыт от анонимного доступа, а некорректные параметры отвергаются.

Различайте корректный отказ и ошибку теста. Если тест ожидает, что конфигурация с двумя master-зонами будет отклонена, такое отклонение означает работающее правило валидации.

Упражнение: выберите один `expect_failures` и объясните, какое ошибочное изменение пользователя он предотвращает. Затем найдите соответствующий `validation` в `variables.tf`.

## Шаг 6 Разобрать два уровня сетевой защиты

Security groups фильтруют доступ на уровне облачной сети и узлов. Kubernetes NetworkPolicy управляет обменом между pod и namespace при поддержке сетевого плагина. Наличие одной защиты не заменяет другую.

В проекте предусмотрены default-deny, разрешение DNS и явные маршруты frontend → backend, ingress → приложение, monitoring → backend, backend → необходимые HTTPS endpoint. Без разрешения DNS приложение может выглядеть исправным, но не сможет разрешить имя сервиса или хранилища.

```bash
uv run python infrastructure/scripts/check-policies.py
```

Эта команда проверяет статический контракт шести политик. Реальное действие allow/deny демонстрируется локальным Kubernetes-тестом следующего этапа, а не этим Python-скриптом.

## Диагностика

| Ошибка | Действие |
| --- | --- |
| Terraform предлагает credentials при локальной проверке | Проверьте `-backend=false` и запуск mock-тестов в нужном каталоге |
| Не удается загрузить provider schema | Проверьте установленный provider, архитектуру, права запуска и ограничения среды |
| fmt завершился ошибкой | Просмотрите форматирование; исправьте отдельно, затем повторите check |
| Mock проходит, но хочется доказать сетевую работу | Используйте локальную интеграцию этапа 3; mock не проверяет пакеты в сети |
| В каталоге появился `.terraform/` | Это рабочий кеш, он исключен из Git; lock-файл сохраняется |

## Результат для сдачи

Нужны общие модули, независимые окружения, раздельные backend keys, примеры параметров, описание выбора платформы и протокол локальных проверок. Успешные mock-тесты показывают корректность проверяемой логики конфигурации. IAM, квоты, доступность GPU и реальная работа Managed Kubernetes в этот результат не входят.

Самопроверка: объясните различие state и кода, bootstrap и приложения, network security group и NetworkPolicy. Затем переходите к [контейнеризации](03_docker_and_kubernetes.md).
