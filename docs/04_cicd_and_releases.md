# Этап 4 CI/CD и управляемая доставка версий

## Цель этапа

Сделать изменение воспроизводимым релизом: проверить код, собрать образы, проверить безопасность, связать артефакты с commit и управляемо перевести трафик. Автоматизация нужна не для самого вызова deploy, а для сохранения одинаковых правил допуска при каждом изменении.

Основные файлы — [GitHub Actions](../.github/README.md), [workflows](../.github/workflows), [контроллер Istio](../scripts/ci/istio_delivery.py), [политика допуска](../infrastructure/kubernetes/istio/release-policy.yaml).

## Шаг 1 Прочитать цепочку jobs

`ci-cd.yml` запускается на push, pull request и вручную. Он вызывает reusable workflows. Сначала quality, затем проверки/сборка/сканирование и локальная Istio-интеграция; результатом успешной подготовки становится release artifact. Дальше описаны staging и production.

| Workflow | Назначение |
| --- | --- |
| `code-quality.yml` | Black, Flake8, actionlint и проверка секретов |
| `build-and-test.yml` | pytest, backend/frontend images, Trivy и integration gates |
| `deploy-staging.yml`, `deploy-production.yml` | Последовательная доставка одного релиза |
| `blue-green-release.yml`, `canary-release.yml` | Ручной выбор стратегии |
| `rollback.yml` | Возврат на сохраненный слот |
| `model-candidate.yml` | Проверка и передача нового модельного кандидата |

Ветка PR не получает кластерные credentials и не публикует релизные images. Production должен использовать те же digest, которые проверялись в staging: повторная сборка по тому же tag может дать другой образ и разрушить эту гарантию.

## Шаг 2 Проверить все, что возможно локально

```bash
uv run python -m pytest tests/test_ci_release.py tests/test_istio_delivery.py -q -ra
uv run black --check src tests scripts docker/backend-entrypoint.py
uv run flake8 --jobs 1 src tests scripts docker/backend-entrypoint.py
```

При установленном actionlint дополнительно выполните `actionlint -shellcheck=''`. Black проверяет форматирование, Flake8 — выбранные правила кода, actionlint — workflow syntax. Trivy проверяет другой класс проблем: утечки секретов и уязвимости. Одна зеленая проверка не заменяет остальные.

В аудите Black обнаружил `scripts/stage6_monitoring.py`. Такой сбой остановит цепочку еще до доставки: он не является ошибкой Kubernetes. Исправление форматирования выполняется отдельно от написания этого гайда.

## Шаг 3 Разобрать релизный контракт

`release.json` содержит commit SHA, CI run ID и digest обоих образов. Deployment берет манифесты из согласованной версии кода. Production проверяет receipt успешного staging для того же релиза. Это защищает от ситуации «в staging тестировали одну сборку, в production попала другая».

Контроллер сохраняет состояние релиза в `mlops/mlops-release-state`. Операции одного environment сериализованы. Если транзакция оборвалась, новый deploy не должен молча считать ее завершенной: сначала восстанавливается известное состояние.

## Шаг 4 Понять Blue-Green

Есть два слота: blue и green. Каждый содержит backend, frontend, Service и ConfigMap. Активный слот обслуживает пользователей, неактивный получает новую версию. После readiness и проверок Istio переключает трафик целиком.

Frontend каждого слота обращается к backend того же цвета. Это важно: новая форма не должна случайно ходить в старый API. Istio Gateway и VirtualService управляют внешним трафиком; текущая схема не включает внутренний mTLS приложений.

Старая версия сохраняется для rollback. Значит, нужны ресурсы для одновременного существования обоих слотов. Обновить все pod старого слота до успешного переключения — значит лишиться быстрого отката.

## Шаг 5 Понять Canary

Canary переводит новые запросы на candidate ступенями 10 → 25 → 50 → 100%. После каждой ступени выполняются проверки. Политика проекта требует минимум 60 выборок, ноль HTTP/transport/contract ошибок, p95 не выше 1 секунды и каждый запрос не дольше 5 секунд. Проверяется фактическое появление ответов всех ненулевых направлений.

Проценты — веса маршрутизации, а не обещание ровно 10 из каждых 100 запросов. Долгие WebSocket-сессии не перескакивают между pod при смене веса. При небольшой выборке нужно убедиться, что candidate вообще получил измеренный трафик.

Критерии доставки не заменяют модельное качество: исправный HTTP 200 может содержать плохой прогноз. Offline AUC/loss и online/segment quality проверяются другими механизмами.

## Шаг 6 Выполнить локальную демонстрацию

```bash
bash scripts/test_istio_local.sh
```

Нужны Docker, kind, kubectl, istioctl, openssl, curl и Python-зависимости. Версии/установка приведены в [инструкции Istio](../infrastructure/kubernetes/istio/README.txt). Скрипт создает собственный kind, устанавливает Istio, тестовый TLS и две синтетические DVC-модели с разными ответами.

Ожидаются восемь сценариев: bootstrap, успешный Blue-Green, отказ после переключения, успешный Canary, отказ Canary, неготовый candidate, подготовка ручного отката и сам rollback. Результаты — в `infrastructure/.evidence/stage4/`.

При ошибке на 50% Canary трафик должен вернуться к baseline, а операция остаться неуспешной. Зеленый deploy после скрытого отказа был бы ложным успехом. В сохраненной проверке успешные окна содержали 3420 запросов без ошибок; намеренные сбои кандидата учитывались отдельно.

## Шаг 7 Сохранить облачный deploy выключенным

Для учебного сценария repository variable `CLOUD_DEPLOY_ENABLED` остается пустой или `false`. Это не отключает код проверки/сборки и конфигурации релизов. Не добавляйте фиктивные credentials ради зеленой отметки облачной доставки.

GitHub Environments, reviewers, DNS/TLS и kubeconfig нужны при отдельном реальном запуске. Имя `environment: production` в YAML само по себе не создает правило approval: оно настраивается в GitHub Settings.

## Диагностика и результат

| Наблюдение | Следующий шаг |
| --- | --- |
| Deploy job skipped | Проверьте условие CLOUD_DEPLOY_ENABLED и ветку; в учебном режиме это ожидаемо |
| Candidate не Ready | Исследуйте pod/DVC/model contract до перевода трафика |
| Gate отклонил версию | Прочитайте evidence по ошибкам и latency, оставьте baseline активным |
| Pending state после аварии | Восстановите связь и выполните предусмотренный rollback |
| Нужен старый релиз, но артефакт удален | Откат требует сохранения образа, модели и runtime-доступов |

Итог — workflows, release contract, политика допуска и доказанный локальный перевод/возврат трафика. Самопроверка: почему digest надежнее tag, почему rollback не означает повторное обучение и почему при первом deploy предыдущей версии еще нет?
