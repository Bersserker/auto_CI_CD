# Этап 1 Подготовка нейросети и ONNX

## Цель этапа

Нужно превратить обученную нейросеть в проверяемый эксплуатационный артефакт: получить вероятности в другом runtime, убедиться в корректности конвертации, оценить компромисс после оптимизации и измерить производительность. Модель с хорошим AUC еще не готова к доставке, если неизвестны ее входной контракт и предобработка.

Основные файлы: [архитектура](../src/neural/neural_network.py), [обучение](../src/neural/train_nn.py), [экспорт](../src/neural/export_onnx.py), [валидация](../src/neural/validate_onnx.py), [quantization](../src/neural/quantize_onnx.py), [benchmark](../src/neural/benchmark.py).

## Шаг 1 Разобрать признаки и разбиение

Обработанная таблица содержит `id`, целевую переменную `default` и признаки. Перед обучением `id` исключается. Из 23 исходных полей вычисляются дополнительные признаки; серверный комплект использует 30 входов NN. Сеть получает значения после StandardScaler, преобразованные в `float32`.

`train_test_split` использует test_size=0.2, random_state=42 и stratify по target. Scaler обучается только на train. Для проверки ONNX воспроизводится то же разбиение и порядок колонок: иначе сравнение окажется сравнением разных объектов или разных входов.

Упражнение: откройте `src/features/build_features.py`, выпишите исходные и вычисляемые колонки. Проверьте, почему в HTTP-запрос не нужно добавлять вычисленные признаки.

## Шаг 2 Разобрать архитектуру и обучение

Исходная PyTorch MLP состоит из Linear → BatchNorm → ReLU → Dropout, повторяет блок со слоями 128/64 и заканчивается одним логитом. Dropout имеет вероятности 0.3 и 0.2. При инференсе вызывается `eval()`: Dropout выключается, BatchNorm использует накопленную статистику.

Для табличных признаков полносвязная сеть позволяет учитывать нелинейные взаимодействия без специальной последовательной структуры. Два умеренных скрытых слоя ограничивают размер артефакта. Это учебное объяснение устройства, которое следует дополнить собственным обоснованием выбора 128/64 и сравнением альтернатив при оформлении задания.

`BCEWithLogitsLoss` принимает логит и сама реализует нужную численно устойчивую форму функции потерь. `pos_weight` учитывает дисбаланс классов. AdamW использует lr=1e-3 и weight_decay=1e-4, обучение длится 25 эпох.

```bash
make prepare-data
make train-nn
```

Команда последовательно обучает сеть, экспортирует ONNX, проверяет совпадение и выполняет quantization. Она перезаписывает соответствующие файлы модели и отчет оптимизации; если нужен исторический комплект, предварительно сохраните его отдельной версией.

Ожидаемые результаты:

| Файл | Содержимое |
| --- | --- |
| `models/best_NN.joblib` | PyTorch state_dict; расширение не делает его sklearn Joblib-моделью |
| `models/best_scaler.joblib` | StandardScaler исходной NN |
| `models/credit_default_model.onnx` | FP32-граф с вероятностью на выходе |
| `models/credit_default_model_quant_dyn.onnx` | Динамически квантованный граф |
| `reports/quantization.json` | Размеры, качество, расхождения и результат gate |

## Шаг 3 Понять экспорт

Экспорт оборачивает сеть в Sigmoid: клиент ONNX получает вероятность, а не логит. Вход называется `features`, имеет форму `[batch, features]`, выход `default_probability` — `[batch, 1]`. Размер batch динамический. StandardScaler не включен в граф и должен применяться вызывающей стороной.

```bash
uv run python -m src.neural.export_onnx
uv run python -m src.neural.validate_onnx
```

Проверка включает корректность графа, одиночный пример, всю test-выборку, форму выхода, конечность значений, диапазон [0,1] и численное совпадение PyTorch/ONNX с rtol=1e-5 и atol=1e-6. Успешная загрузка файла сама по себе этих свойств не доказывает.

Если экспорт прошел, а вероятности не совпали, проверьте `eval()`, scaler, порядок колонок, тип float32, применение Sigmoid и пару весов/ONNX. Не увеличивайте допуск, пока не найдена причина расхождения.

## Шаг 4 Оценить оптимизацию

```bash
uv run python -m src.neural.quantize_onnx
python -m json.tool reports/quantization.json
```

Dynamic QUInt8 уменьшает представление части весов и использует динамическое квантование активаций. Проверка сравнивает INT8 с исходной ONNX FP32, а не напрямую с PyTorch. Gate допускает абсолютное падение каждой проверяемой метрики не более 0.01.

В сохраненном отчете размер изменился 61 453 → 22 202 байта, AUC упал на 0.001018, F1 — на 0.007491. Максимальное отличие отдельных вероятностей 0.163588 показывает, почему нужно смотреть и агрегированное качество, и характер расхождений. Для решений около порога 0.5 даже небольшое изменение вероятности может поменять класс.

Динамическое квантование зависит от активаций конкретного batch. Поэтому сравнение runtime при batch=1 выполняется с локальным эталоном batch=1. Не сравнивайте одиночный online-ответ с заранее рассчитанным большим INT8-batch без учета этого свойства.

## Шаг 5 Измерить скорость

```bash
make benchmark-nn BENCHMARK_ARGS="--devices cpu --output-dir artifacts/benchmark-study --label study-cpu"
```

Для GPU после проверки совместимости драйвера и пакетов можно отдельно использовать `make benchmark-nn-gpu`. Эта цель устанавливает GPU-пакеты во временный каталог и выполняет benchmark. Чистый INT8 CUDA может быть пропущен при CPU fallback; запись skipped не является измеренной GPU-производительностью.

Скрипт варьирует CPU affinity, batch и число клиентов. Отдельный процесс изолирует backend, прогрев исключается. Throughput считается по общему времени выполнения, а latency — для запроса. В замер входят scaler и инференс, но не HTTP/JSON/сеть. Больше CPU не обязано ускорять маленькую сеть: потоки и накладные расходы могут ухудшить хвост распределения.

Сравнивайте p50/p95/p99, req/s, объектов/с, RSS и загрузку CPU/GPU. Для batch=256 запросов/с и объектов/с — разные величины. Один быстрый повтор не заменяет несколько повторений и оценку худших результатов.

## Как завершить этап

Сохраните описание архитектуры, версии входных данных и кода, согласованный набор весов/scaler/ONNX, отчет parity, quantization и benchmark с командами воспроизведения. Рекомендацию ресурсов ограничьте измеренным режимом: «подходит как стартовая локальная CPU-конфигурация», если реальный HTTP-сервис не измерялся.

Минимальная регрессия:

```bash
uv run python -m pytest tests/test_neural_benchmark.py tests/test_onnx_serving.py -q
```

## Разбор ошибок и самопроверка

| Симптом | Что проверить |
| --- | --- |
| ONNX ожидает другое число входов | Feature engineering и правильный scaler |
| Вероятности вне [0,1] | Не возвращается ли логит без Sigmoid |
| INT8 меньше, но медленнее | Размер NN, batch и поддерживаемые операторы runtime |
| CUDA доступна, но вычисления на CPU | Профиль размещения операторов и CPU fallback |
| После обучения сервис отвечает старыми значениями | Кеш загрузки модели; нужен перезапуск процесса |

Объясните, почему конвертация и quantization проверяются разными допусками и почему эталонная выборка должна оставаться одинаковой. Далее переходите к [Terraform](02_terraform.md).
