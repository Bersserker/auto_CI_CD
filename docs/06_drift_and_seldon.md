# Этап 6 Дрифт качество и управление версиями моделей

## Цель этапа

Добавить наблюдение за данными и качеством, которое не сводится к HTTP-доступности, и научиться сравнивать две модели без немедленной замены основной. Здесь используются настоящие ONNX FP32/INT8, Evidently, Seldon Core 2 и отдельный gateway.

Подробные контракты находятся в [инструкции этапа 6](../monitoring/stage6/README.md), логика drift — в [model_drift.py](../src/monitoring/model_drift.py), A/B и shadow — в [gateway.py](../src/model_management/gateway.py).

## Шаг 1 Различать три сигнала

Data drift означает изменение распределения входов. Performance decay означает ухудшение измеренного качества при известных фактических исходах. Concept drift связан с изменением зависимости target от признаков; в этом проекте используется диагностический сигнал подозрения на такое изменение.

Data drift не доказывает ухудшение качества. И наоборот: при прежнем распределении признаков зависимость между ними и дефолтом может измениться. Поэтому одного PSI недостаточно для вывода о необходимости замены модели.

| Проверка | Нужны ли targets | Что можно заключить |
| --- | --- | --- |
| Распределение признаков | Нет | Поток отличается от эталона |
| AUC и log loss | Да, зрелые | Измеренное качество изменилось |
| Остатки в группах и отсутствие feature drift | Да | Есть основание подозревать concept drift |

## Шаг 2 Зафиксировать эталон и provenance

Демонстрация берет 2000 reference и другие 1000 current строк из held-out части. Обучающие объекты исключены. Manifest фиксирует ID, seed и SHA256 данных/модели/scaler. Эталон не должен незаметно меняться при каждом запуске: иначе исчезает смысл сравнения.

PSI-порог — 0.2, data drift объявляется при превышении у не менее 20% исходных признаков. Минимальное окно — 200 строк. Вероятность тоже анализируется, но не включается в знаменатель доли исходных признаков.

Запустите только offline-часть:

```bash
make stage6-drift
```

В `artifacts/stage6/drift/` появятся manifest, HTML/JSON и Prometheus-метрики для baseline, data-drift и concept-drift. Если provenance существующего эталона не совпадает, выберите новый output-каталог через CLI, не удаляйте проверку соответствия.

## Шаг 3 Понять задержку фактического исхода

При выдаче прогноза дефолт еще не известен. Нельзя заменить отсутствующую метку нулем или считать собственный прогноз модели правильным target. Нужен внешний наблюденный исход после горизонта 30 дней.

Таблица predictions содержит `request_id`, `predicted_at`, признаки и probability. Таблица outcomes — `request_id`, target, matured_at и observed_at. Первое время задает окончание горизонта, второе — момент доступности результата системе. As-of определяет, какие исходы были известны на дату расчета.

Join строго one-to-one. Дубликаты, наблюдение до maturity, некорректные времена и слишком короткий горизонт отклоняются. Исходы после as-of не используются. Для качества требуется минимум 90% зрелых меток, оба класса и достаточное число объектов.

Если меток нет, качество неизвестно. Неизвестное состояние не является сообщением «все хорошо». В качестве упражнения объясните, почему вчерашняя заявка не подходит для оценки дефолта через 30 дней.

## Шаг 4 Интерпретировать симуляции

Baseline использует обычный current. В data-drift меняются денежные суммы и просрочки, затем заново рассчитывается настоящий ONNX-прогноз. В concept-drift сохраняются признаки и вероятности, а targets меняются искусственно.

Decay определяется падением AUC более 0.03 или ростом loss более 0.05. Остаток `target - probability` анализируется по группам `pay_0 > 0` и остальным; требуется не менее 50 размеченных строк в группе. Подозрение concept drift возникает при ухудшении качества без feature drift и изменении остатков более 0.1.

Это демонстрационные правила, а не универсальное доказательство изменения P(y|X). Если признаки и качество изменились одновременно, причина смешана и требует исследования.

## Шаг 5 Запустить модельный runtime

```bash
make stage6-experiment
```

Команда поднимает Seldon Core 2.10.0 в Docker Compose, регистрирует FP32 и INT8 и выполняет эксперимент. Scheduler управляет жизненным циклом, agent/MLServer обслуживают модель, Envoy предоставляет inference-маршрут. A/B и shadow реализованы gateway перед Seldon.

Проверьте адреса:

- `http://localhost:18080/docs` — gateway;
- `http://localhost:18081/` — демонстрационные HTML Evidently;
- `localhost:19004` — scheduler gRPC.

`ModelAvailable` означает, что нужная версия готова к обслуживанию. Наличие Docker-контейнера scheduler без готовой модели недостаточно.

## Шаг 6 Разобрать A/B и shadow

A/B выбирает модель по стабильному hash `X-Request-ID`: приблизительно 50% FP32 и 50% INT8. Одинаковый ID попадает в одну группу. Для повторных заявок одного клиента в реальном эксперименте потребовалось бы согласованное стабильное назначение на уровне участника.

Shadow возвращает клиенту только FP32, а копию отправляет INT8 асинхронно. Очередь ограничена; при переполнении копия пропускается, primary не блокируется. Ошибка shadow учитывается отдельно и не должна ломать основной ответ.

Эксперимент делает 200 A/B и 200 shadow запросов, сверяет primary с локальным ONNX batch=1 и ждет shadow-пары. `comparison.json` содержит counts, качество на сопоставимых объектах, максимальное расхождение и compatibility gate. Онлайн причинный эффект по такой исторической выборке не оценивается.

```bash
python -m json.tool artifacts/stage6/comparison.json
make stage6-test
```

Падение AUC не более 0.01 и max delta не более 0.01 — preliminary gate этого эксперимента. Это отдельная проверка от batch-метрик quantization этапа 1. Автоматического promotion в gateway нет.

## Шаг 7 Подключить наблюдение и диагностировать

При уже работающем стенде этапа 5:

```bash
make stage6-monitoring
```

Откройте Grafana, дашборд drift/моделей и период Last 30 minutes. Проверьте targets и признаки симуляции. Если нет новых данных, повторите только трафик:

```bash
uv run --group monitoring python -m scripts.stage6_experiment
```

При 503 смотрите логи `docker compose -p scoring-stage6 -f docker-compose.stage6.yml logs scheduler agent mlserver`, регистрацию моделей и комплект scaler/ONNX. При data drift проверьте эталон и схему, при decay — зрелость, coverage и join. Не заменяйте эталон только ради снятия алерта.

Остановка:

```bash
make stage6-down
```
